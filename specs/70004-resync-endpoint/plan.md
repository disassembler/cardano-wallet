# Implementation Plan: Wallet Chain Continuity Recovery and Rescan Endpoint

**Branch**: `70004-resync-endpoint` | **Date**: 2026-09-01 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/70004-resync-endpoint/spec.md`

## Summary

Fix the permanent wallet-worker crash caused by a chain continuity error in `restoreBlocks`, and add a `POST /v2/wallets/{walletId}/rescan` endpoint as a manual failsafe. The engine fix catches the continuity error at the `restoreWallet` level, rolls back to the deepest available checkpoint, and re-initiates chain sync — all without human intervention. The rescan endpoint provides a genesis-reset path for wallets whose checkpoint window is too shallow to find a valid intersection.

## Technical Context

**Language/Version**: Haskell (GHC 9.8.x via nix flake)
**Primary Dependencies**: cardano-wallet internal libraries (wallet, api, network-layer, db); Servant (REST API); SQLite via delta-store; STM; async
**Storage**: SQLite (one file per wallet), accessed via `DBLayer` abstraction using delta-based append-only mutations
**Testing**: HSpec (unit), custom IO-based integration test framework against local cardano-node cluster (multi-era)
**Target Platform**: Linux musl static, Windows cross-compiled, macOS Intel + Apple Silicon
**Project Type**: web-service (Servant REST API) + library (wallet engine)
**Performance Goals**: Rescan initiation < 1s; automatic recovery within one chain sync reconnect cycle; no measurable throughput regression on the normal block-application path
**Constraints**: -Wall / -Werror in release builds; Fourmolu 70-char line limit; no new external dependencies; OpenAPI spec must be updated for the new endpoint; delta-based storage semantics must be preserved
